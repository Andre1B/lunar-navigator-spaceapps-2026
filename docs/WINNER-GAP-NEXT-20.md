# Twenty more global winners: make one interaction explain the decision

Research date: 2026-11-14. These **20 category winners from 2012–2015** are additional to [WINNER-LESSONS.md](WINNER-LESSONS.md), [CLARITY-CORRECTIONS.md](CLARITY-CORRECTIONS.md), [WINNER-GAP-20.md](WINNER-GAP-20.md) and the earlier private 2020–2025 inventory. People's Choice, finalists and honorary mentions are excluded. The original 2012 category names are retained.

Award evidence: the official [2015 awards](https://2015.spaceappschallenge.org/award/), [NASA 2014 announcement](https://www.nasa.gov/news-release/nasa-announces-global-award-winners-of-the-2014-international-space-apps-challenge/), [2013 mission report](https://assets.spaceappschallenge.org/media/documents/SpaceApps2013_MissionReport.pdf) (printed pages 41–43) and [2012 announcement](https://2012.spaceappschallenge.org/blog/2012/05/18/global-winners-announced/) confirm all twenty. These sources establish awards, **not why individual judges selected a project**. Transfers below are our interpretations. Team descriptions establish proposals and reported work, not independently measured performance.

## Small, relevant backlog

1. **One nearby-point comparison.** A “Compare nearby point” action could select a generated neighbor while keeping arrival, stay and height unchanged. Immediately show the same Sun/Earth metrics and the changed consequence. The two new points support this experiment; they were selected by fixed coordinate offsets before visibility calculations, not optimized or endorsed as landing sites. Do not generalize their contrast to every location one kilometre away.
2. **Make result inspection purposeful.** A result card should lead to the corresponding observer, time and Sun/Earth direction, with the reason still visible and a return path preserving the comparison. SkyWatch provides a concrete precedent. Current inspection controls cover much of this; check the complete task before adding another mode.
3. **Ask a familiar question before teaching terminology.** “What changes nearby?” and “What if we arrive later?” are meaningful before “azimuth” or “visible-disc fraction.” Explain height as the observer's height above the modeled surface. Keep the distinction between light during a stay and the disc visible at one instant beside the relevant number.
4. **Use motion to reveal a consequence.** The existing before/after-event inspection and input → horizon → duration explanation fit this lesson. A short transition should show which input changed and what happened; respect reduced motion and retain a static answer. More cinematic movement does not itself improve understanding.

These are a compact backlog, not twenty feature requests. The remaining evidence gap is an **uncoached newcomer task**: can someone identify the app's purpose, explain one comparison, distinguish current disc from time sunlit, change height, inspect and return? This research does not measure that outcome. Table/text comparison and export must remain useful without 3D; no winner justifies inferring safety, power or communications from visibility alone.

## 2015

### 1. NYSpaceTag — Best Use of Data

**Observed:** the [submission](https://2015.spaceappschallenge.org/project/nyspacetag/) identifies a search barrier: people lack specialist keywords. It proposes related concepts leading to datasets. The [repository](https://github.com/jonroberts/nasaMining) directory and `readme.md` describe keyword extraction and a graph interface.

**Lunar transfer:** use goal wording and reveal specialist terms after an answer. A new search engine is unnecessary. Beginner success was not measured here.

### 2. Valkyrie — Best Use of Hardware

**Observed:** the [submission](https://2015.spaceappschallenge.org/project/valkyrie/) describes glove, voice and application controls, configurable gestures and a stop on connection loss. Its linked [Bitbucket source](https://bitbucket.org/rapiddevelopmentcrew/valkyrie/src) was not inspected.

**Lunar transfer:** make direct actions and paused/running feedback explicit. Existing Play and aiming controls are the relevant surface; no glove or mandatory gesture follows. Accuracy and space suitability claims remain unverified.

### 3. ArachnoBeeA — Best Mission Concept

**Observed:** the [submission](https://2015.spaceappschallenge.org/project/arachnobeea/) describes a cargo handling robot. The [repository inventory](https://github.com/aleksandarbozic/nasa_space_apps_2015) contains CAD, video, sensor code and documents for locating, grabbing, flight and docking; binary documents were not opened.

**Lunar transfer:** present an explicit task and its stages. Motion should explain a selected location or event rather than create an unrelated robot narrative. Inventory is not a demonstration of autonomous flight.

### 4. CROPP — Galactic Impact

**Observed:** the [submission](https://2015.spaceappschallenge.org/project/cropp-coltures-risks-observation-and-prevention-platform/) connects local sensors and satellite observations to a farmer's field status. The linked [repository](https://github.com/blackecho/cropp) returned 404.

**Lunar transfer:** give a simple consequence while preserving source scale and limits. Distinguish nearby terrain from distant terrain coverage in explanations. Do not convert partial visibility information into an unsupported green “safe” score.

### 5. Tracking and Sensing through Android Robotics / Robot Tracker — Most Inspirational

**Observed:** the [submission](https://2015.spaceappschallenge.org/project/tracking-and-sensing-through-android-robotics/) uses familiar smartphone sensors for a robot platform and explains a local access/cost problem. The linked [source](https://github.com/enigmerald/TSAndroid) returned 404.

**Lunar transfer:** a normal browser and familiar controls should answer the core question without special equipment. Current text/table paths already support this direction; hardware performance was not tested.

## 2014

### 6. SkyWatch — Best Use of Data

**Observed:** the [submission](https://2014.spaceappschallenge.org/project/skywatch/) describes event cards with explanations and source links; clicking a card points Google Sky to the event. Filters and raw XML remain available. The [repository](https://github.com/ryanovas/alert-alert) inventory and README confirm an event-oriented application.

**Lunar transfer:** connect a comparison answer directly to its relevant scene and moment. Keep raw evidence optional and accessible. This is a stronger interaction analogy than copying the appearance of a star map.

### 7. Android Base Station — Best Use of Hardware

**Observed:** the [submission](https://2014.spaceappschallenge.org/project/androidbasestation/) proposes simple startup and automatic satellite tracking while identifying outdoor tests still to do. The [repository](https://github.com/GlenSearle/SpaceBaseStationForAndroid) contains Arduino, interface and calculation files; its README is only a placeholder.

**Lunar transfer:** make one meaningful preset easy, while labeling unsupported conditions honestly. Automatic camera targeting is useful; automatic “best landing site” selection is not supported by Lunar's model.

### 8. Aurora Wearables: Fashion meets Function — Best Mission Concept

**Observed:** the [submission](https://2014.spaceappschallenge.org/project/aurora-wearables---fashion-meets-function/) distinguishes a reported ISS-overflight light patch from speculative additions. The [repository inventory](https://github.com/spaceappssuit/suit) contains Arduino/electric imp files. No hardware was run.

**Lunar transfer:** connect an event to a visible cue and distinguish calculated results, illustrative terrain brightness and future work. A team statement about judges is not an independently documented global judging rationale.

### 9. Yorbit — Most Inspiring

**Observed:** the [submission](https://2014.spaceappschallenge.org/project/yorbit/) personalizes satellite imagery by place and date. The [repository](https://github.com/ingenology/yorbit) README and directory were read. The historical page describes finishing work and early access, not a current verified service.

**Lunar transfer:** keep location, arrival and window visible in answers and inspection; preserve them on return. Existing export carries a reproducible scenario. A screenshot alone cannot establish its inputs.

### 10. SkySnapper — Galactic Impact

**Observed:** the [submission](https://2014.spaceappschallenge.org/project/sky-snapper/) starts with photographing the sky, then connects analysis to a map and explanation. Its linked [GitHub source](https://github.com/Benn83uk/SpaceAppsChallenge2014) returned a repository-moved response; source contents were not inspected.

**Lunar transfer:** connect one input action to a local result and an explanation. Do not treat rendered ground brightness as a scientific measurement. The project's pollution inference was not independently validated here.

## 2013

### 11. Sol — Best Use of Data

**Observed:** the [submission](https://2013.spaceappschallenge.org/project/sol) uses familiar Earth weather to introduce Mars weather. The [repository README](https://github.com/ingenology/sol) identifies the mobile application and its Mars/Earth data sources.

**Lunar transfer:** familiar comparisons can introduce an unfamiliar environment. Explain “how long without direct Sun during your stay” before a technical horizon lesson. Avoid implying Earth-like weather, twilight or operational conditions on the Moon.

### 12. ISS Base Station — Best Use of Hardware

**Observed:** the [submission](https://2013.spaceappschallenge.org/project/iss-base-station) combines a map, physical pointing and augmented reality; the [map repository inventory](https://github.com/DanGe42/iss-leaflet) contains application, routes and views. Other linked hardware implementations were not fully inspected.

**Lunar transfer:** coordinate overview and observer direction around one selected event. Existing map/scene views can do this without AR or another camera paradigm. Map agreement alone does not validate terrain occultation.

### 13. Popeye on Mars — Best Mission Concept

**Observed:** the [submission](https://2013.spaceappschallenge.org/project/pom) states mission assumptions, including location and a 45-day scenario. The [repository](https://github.com/hsgr/pom) README and inventory include greenhouse design, electronics and Blender material.

**Lunar transfer:** state the scope before the conclusion: selected point, observer height and evaluated dates. Keep the new neighbor points explicitly our selections. A concept award is not evidence of crop survival or habitat feasibility.

### 14. NASA Greener Cities Project — Galactic Impact

**Observed:** the [submission](https://2013.spaceappschallenge.org/project/street-view-for-climate-data) connects local sensors, neighborhood aggregation and global climate information. The [repository inventory](https://github.com/KurtCode/GreenerCity) includes map and heat-view HTML files.

**Lunar transfer:** show why a local observation differs from a broad overview. The nearby-point pair can reveal that regional proximity does not guarantee equal terrain horizons. Do not imply measurements at arbitrary map pixels.

### 15. T-10 — Most Inspiring

**Observed:** the [submission](https://2013.spaceappschallenge.org/project/t-10) turns orbital geometry into a selected target, warning and countdown, with day/night and weather constraints. The [server README](https://github.com/jpgneves/t-10_server) lists calculation and service dependencies; nothing was executed.

**Lunar transfer:** time is useful when attached to a consequence. Existing rise/set inspection can answer “when does this change?” Retain event resolution and window-boundary labels; a countdown must not suggest more precision than the event model.

## 2012

The official winner list and [project gallery](https://2012.spaceappschallenge.org/) remain available. All five individual solution links recovered from the official historical inventory now lead to missing pages. Evidence below therefore uses official descriptions and the specifically identified surviving materials, not reconstructed screenshots or imagined workflows.

### 16. Planet Hopper — Most Inspiring

**Observed:** the [official 2013 follow-up challenge](https://2013.spaceappschallenge.org/challenge/exploring-asteroids-planet-hopper-20) explicitly criticizes the previous winner for assuming visitors understand its purpose and data; it requests context and narrative. Its linked [Kepler Explorer README](https://github.com/Floppy/kepler-explorer) identifies an educational explorer.

**Lunar transfer:** winning does not resolve comprehension. State the question and the meaning of the first result before offering exploration. This documented organizer critique is stronger evidence than guessing why judges liked a project.

### 17. Vicar2png — Best Use of Data

**Observed:** official descriptions identify conversion of mission images into familiar PNG files. A [team member's submission description](https://vimeo.com/41634392) connects the converter to the challenge; the matching [repository README](https://github.com/jesstess/vicar2png) was read. The video itself was not watched; the broken original page cannot confirm its historical source link.

**Lunar transfer:** make specialist data usable through familiar outputs. Existing plain text, tables and JSON export are valuable. No new image converter is needed, and source availability is not proof of data fidelity.

### 18. Growing Fruits: Pineapple Project — Most Disruptive

**Observed:** the official announcement describes combining location and growing conditions. A subsequent [team-authored paper](https://www.scitepress.org/Papers/2013/43318/43318.pdf) explains the 2012 origin, constrained pilot data and an SMS interface chosen for users' actual access; it distinguishes current design from future expansion.

**Lunar transfer:** prioritize the smallest interface that answers the question, with explicit coverage. A graphically richer interface is not automatically more accessible. Crop recommendations do not justify a lunar safety ranking; no source code was recovered from the original page.

### 19. Strange Desk — Most Innovative

**Observed:** official descriptions identify shared observations and aggregate patterns. NASA's [2012 Open Government status report](https://ntrs.nasa.gov/api/citations/20130009003/downloads/20130009003.pdf) independently records the award and social observation purpose. No working original solution page or source repository was recovered.

**Lunar transfer:** connect a concrete observation to its broader pattern, while identifying its evidence type. A selected event and the stay timeline already offer this relationship. Crowd reports would add an unsupported scientific authority and are unnecessary.

### 20. Growers Nation — Galactic Impact

**Observed:** the official description combines unused land, climate and crops. A [research organization's 2014 newsletter](https://geo-wiki.org/assets/newsletters/Geo-Wiki-Newsletter-Summer2014.pdf) describes a later mobile version explaining what grows and when to plant or harvest. That later version is not treated as proof of the 2012 implementation.

**Lunar transfer:** answer a place-and-time question with a consequence and next inspection. Lunar's delayed-arrival comparison fits this pattern. No current demo, original repository or user-outcome measurement was established.

## Evidence limits and adoption boundary

All twenty award identities are confirmed; fifteen original project pages from 2013–2015 were read. Repository directories and selected READMEs were inspected where identified above, not every file or historical submission commit. Broken repositories, redirects, unread binary assets and later versions are explicitly separated. No competitor code was installed, executed or copied; these are references and interaction lessons, not dependencies.

This study does not establish scientific equivalence, winning causes, present-day service availability or improved Lunar usability. Keep the physical horizon model authoritative, retain source/coverage metadata, and verify any adopted interaction with the same comparison inputs. Human comprehension remains an explicit measurement gap.

## Integration checkpoint (implemented, verification pending)
- Home now asks a concrete landing-delay question and offers +3/+7/+14 days using the same comparisonRows engine as Compare/export. The CTA carries the exact experiment settings forward.
- The nearby alternative shortcut changes only the alternative point; original point, dates, duration and height are preserved. The two neighbor points were physically calculated, not assigned invented results.
- Inspecting a comparison opens the surface sky at the exact selected arrival, paused; the comparison settings remain separate.
- Continuous Sun/Earth following and finite section/control motion explain the changing geometry. Reduced motion remains respected.
- Code review and directed root smoke are complete; the independent six-site matrix and production gates are still pending. Actual uncoached novice comprehension has not been measured.
